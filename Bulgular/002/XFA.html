CLIXML Fragment Splitting

PowerShell CLIXML Deserialization as a Fragment Reconstruction Mechanism
Researcher: Eneshan Erdoğan Karaca Team: BoxStrike Published: August 2026 Classification: Public

1. Executive Summary

CLIXML Fragment Splitting is a PowerShell execution technique in which an encoded PowerShell payload is divided into multiple Base64 fragments and represented as serialized string values inside a CLIXML structure. The target PowerShell process passes the CLIXML representation through ConvertFrom-CliXml, obtains the serialized string values, reconstructs the original Base64 stream, decodes it, and creates a ScriptBlock from the resulting PowerShell source.

The technique combines three native PowerShell mechanisms: CLIXML deserialization, Base64 representation, and runtime ScriptBlock creation. The important property of the method is that the payload representation presented to the execution layer is distributed across multiple serialized string objects rather than stored as one contiguous PowerShell command.

The research PoC was executed using the fragment-reconstruction workflow described in this report. The payload used during testing is retained in the PoC section and in the original Base64 material below so that the experiment remains reproducible.

2. Technical Concept

2.1 Payload Representation

The starting point is a PowerShell command represented as UTF-8 bytes and encoded with Base64. The resulting Base64 stream is divided into fragments. The fragments are placed into individual CLIXML string values.

The fragmentation occurs at Base64 character boundaries. A complete Base64 stream has a length divisible by four when padding is present in the normal form. Fragmenting the stream therefore preserves character order while allowing the original stream to be reconstructed by concatenation.

Input

PowerShell source → UTF-8 bytes → Base64 representation.

Storage

Base64 representation → fragments → CLIXML string objects.

2.2 CLIXML Representation

CLIXML is the XML-based serialization format used by PowerShell. A serialized string is represented by an <S> element and its surrounding object metadata. Multiple objects can therefore carry separate portions of the same encoded data. 

<Objs Version="1.1.0.1"
      xmlns="http://schemas.microsoft.com/powershell/2004/04">
  <Obj RefId="0">
    <TN>
      <T>System.String</T>
    </TN>
    <S>Base64Fragment_1</S>
  </Obj>

  <Obj RefId="1">
    <TN>
      <T>System.String</T>
    </TN>
    <S>Base64Fragment_2</S>
  </Obj>
</Objs>

Figure 1 — CLIXML representation containing multiple serialized string fragments.

3.1 Deserialization

The CLIXML representation is supplied to ConvertFrom-CliXml. PowerShell interprets the XML according to the CLIXML serialization format and reconstructs the serialized values. The exact returned PowerShell object depends on the serialized structure; the PoC therefore treats the returned result as a collection of values and explicitly extracts the string content required for reconstruction.

3.2 Fragment Reconstruction

The individual Base64 fragments are not decoded independently. They are first restored to their original order and concatenated. This produces the original contiguous Base64 stream. 

$segments = $xmlPayload | ConvertFrom-CliXml

$combinedBase64 = $segments -join ''

$fullCommand = [System.Text.Encoding]::UTF8.GetString(
    [System.Convert]::FromBase64String($combinedBase64)
)

This ordering is significant. Decoding each fragment independently can fail or produce incorrect byte boundaries when the split does not correspond to independent Base64-encoded byte sequences. The intended operation is therefore: 

CLIXML fragments
      ↓
deserialized string values
      ↓
ordered concatenation
      ↓
complete Base64 stream
      ↓
Base64 decoding
      ↓
UTF-8 PowerShell source

3.3 Runtime ScriptBlock Construction

After Base64 decoding, the resulting UTF-8 data is PowerShell source code. The PoC creates a ScriptBlock from this source and invokes it through the call operator. 

$fullCommand = [System.Text.Encoding]::UTF8.GetString(
    [System.Convert]::FromBase64String($combinedBase64)
)

& ([scriptblock]::Create($fullCommand))

The execution primitive is therefore separate from the serialization primitive: ConvertFrom-CliXml reconstructs the serialized values, Base64 decoding reconstructs the source representation, and [scriptblock]::Create() converts the resulting source into executable PowerShell code.

5. Fragment Splitting Model

The core operation can be represented mathematically as an ordered sequence of Base64 fragments: 

B = F₁ || F₂ || F₃ || ... || Fₙ

where:

B  = original Base64 stream
F₁...Fₙ = ordered fragments
|| = string concatenation

After deserialization, the values are concatenated without modifying their contents: 

$combinedBase64 = $segments -join ''

The resulting value is then equivalent to the original Base64 stream B and is passed to FromBase64String().

7. Distinction from Ordinary XML Parsing

The mechanism described in this report is specifically based on CLIXML deserialization. This is different from loading the same XML syntax as an ordinary XML document with the PowerShell [xml] type accelerator.

Ordinary XML Parsing

[xml]$xml creates an XML document representation. XML elements are accessed as XML data and are not automatically reconstructed as serialized PowerShell objects.

CLIXML Deserialization

ConvertFrom-CliXml interprets the input according to PowerShell's serialization format and reconstructs the serialized values represented by the document.

This distinction is the defining technical property of the present technique. The research is not based on XPath execution and does not require ordinary XML property traversal to reconstruct the serialized objects.

11. Security Research Implications

The technique demonstrates that PowerShell's serialization infrastructure can be incorporated into a payload reconstruction chain. The relevant feature is not the Base64 encoding by itself, but the combination of serialized string representation, fragment ordering, deserialization, reconstruction, and runtime code generation.

From an analysis perspective, the chain creates several distinct representations of the same payload during execution:

  • Base64 payload stream;
  • individual Base64 fragments;
  • CLIXML serialized string objects;
  • deserialized PowerShell string values;
  • reconstructed Base64 stream;
  • decoded PowerShell source;
  • runtime-created ScriptBlock.

The transition between these representations is the central subject of the research. A detector that observes only one representation of the payload can therefore have a different view of the sample than an analysis system that correlates the complete transformation chain.

12. Conclusion

CLIXML Fragment Splitting demonstrates a PowerShell-native method for distributing an encoded payload across multiple CLIXML serialized string values and reconstructing that payload at runtime.

The method consists of Base64 encoding, ordered fragmentation, CLIXML representation, ConvertFrom-CliXml deserialization, fragment concatenation, Base64 decoding, UTF-8 source reconstruction, and ScriptBlock execution.

The PoC confirms the complete reconstruction path in the tested environment. The Base64 payload used during testing and the corresponding reconstruction logic are retained in this report to preserve the reproducibility of the research.

The principal technical finding is the use of CLIXML deserialization as an intermediate payload-reconstruction layer rather than merely as a mechanism for restoring ordinary serialized administrative data. The resulting execution chain provides a concrete example of how native PowerShell serialization functionality can participate in runtime payload assembly.
