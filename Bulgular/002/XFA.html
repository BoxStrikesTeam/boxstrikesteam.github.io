BoxStrike · Technical Report

XPath Fragment Assembly (XFA) – A PowerShell/XML-Based Payload Assembly and Defense Evasion Technique
Published: 9 August 2026 Author: BoxStrike Research Version: 1.5 Classification: Public

1. Executive Summary

This report documents XPath Fragment Assembly (XFA), a PowerShell-based execution pattern that uses native XML parsing, structured XML objects, in-memory payload reconstruction, and dynamic PowerShell execution.

The technique is designed around a simple concept: payload data is represented inside an XML structure rather than being presented directly as executable PowerShell source. The XML document is parsed by PowerShell, the relevant data is extracted from the resulting object structure, reconstructed in memory, decoded, and finally passed to a dynamically created PowerShell ScriptBlock.

From an offensive perspective, this provides an alternative payload representation in which the initial content presented to a security product may primarily resemble structured XML and ordinary PowerShell object handling rather than a directly visible command.

From a defensive perspective, the important characteristic is not any individual XML or Base64 operation. The security-relevant behaviour is the complete sequence of XML parsing, payload extraction, reconstruction, decoding, and dynamic execution.

Research scope: XFA is presented as a research term describing this execution pattern. The existence of the technique does not by itself demonstrate universal EDR/AV bypass. Detection effectiveness must be evaluated experimentally against individual products, configurations, logging policies, and PowerShell versions.

2. Introduction

PowerShell provides a number of native capabilities that are routinely used for legitimate administration, automation, configuration management, and system scripting. XML parsing is one such capability and is commonly encountered in administrative workflows.

XFA investigates how these legitimate capabilities can be chained together to transport and reconstruct executable PowerShell content at runtime. The method does not depend on PowerShell deserialisation mechanisms such as ConvertFrom-CliXml or PSSerializer.Deserialize. Instead, the XML document is interpreted through PowerShell's native XML object representation.

This distinction is important because the technique does not require an attacker to rely on PowerShell object deserialisation in order to obtain the payload from XML. The XML acts as a container and representation layer, while the final execution occurs after the payload has been reconstructed in memory.

3. Attack Chain

The complete XFA execution chain can be represented as follows: 

```

Payload preparation
│
▼
Payload encoding
│
▼
XML embedding
│
▼

│
▼
PowerShell XML parsing
│
▼

│
▼

│
▼

│
▼

│
▼

```

3.1. Stage 1 – Payload Preparation

The attacker begins with a PowerShell command or script that represents the desired post-delivery action. Instead of presenting this source directly, the payload is transformed into a representation that can be stored inside the XML structure.

This separation creates two conceptual layers: the transport/container representation and the final executable PowerShell representation.

3.2. Stage 2 – XML Embedding

The encoded payload is placed inside an XML document using a <S> element within a CLIXML-style structure.

The XML structure provides a legitimate serialization-like appearance while allowing the payload to remain separate from the surrounding PowerShell execution logic.

3.3. Stage 3 – Delivery

An attacker could deliver the XML representation through several mechanisms, including a file, embedded script content, a downloaded resource, or another application-controlled data channel.

The technique itself is independent of the initial delivery mechanism. Its relevant property begins when PowerShell receives and processes the XML representation.

3.4. Stage 4 – XML Parsing

PowerShell converts the XML document into an XML object using the native [xml] type conversion mechanism.

The resulting object exposes the XML hierarchy through PowerShell's object/property navigation. The relevant <S> elements can consequently be accessed without invoking PowerShell's XML deserialisation functionality.

3.5. Stage 5 – Payload Extraction and Assembly

The extracted XML data is treated as the payload representation and reconstructed in memory.

In a fragmented implementation, multiple XML nodes can represent consecutive portions of the encoded payload. These values can be concatenated before decoding. In the PoC presented in this report, the payload is represented by a complete XML element.

3.6. Stage 6 – Decoding

After the payload representation has been reconstructed, the encoded content is decoded into its PowerShell source representation.

This stage is important from a defensive perspective because it creates a transition from an apparently structured data representation to executable script content.

3.7. Stage 7 – Dynamic Execution

The resulting PowerShell source is passed to [scriptblock]::Create() and subsequently invoked.

At this point, the execution chain has transitioned from XML data processing into dynamic PowerShell execution.

4. Why the Technique Is Security-Relevant

The security relevance of XFA originates from the difference between the representation of the payload during the initial processing stages and the representation that ultimately reaches the execution stage.

A security product may observe XML parsing, object navigation, string handling, and other operations that individually have legitimate administrative uses. The final malicious intent may only become apparent after several operations have been chained together.

Therefore, an effective detection strategy should not necessarily treat XML parsing itself as malicious. Instead, defenders can correlate the following behavioural sequence: 

```

XML parsing
+
XML payload extraction
+
encoded data processing
+
dynamic ScriptBlock creation
+
PowerShell execution
```

The presence of this sequence can provide a stronger behavioural signal than any individual operation in isolation.

5. Why Avoid Deserialisation?

Traditional PowerShell XML workflows may involve mechanisms such as ConvertFrom-CliXml or PSSerializer.Deserialize. XFA deliberately does not depend on those mechanisms.

Instead, the XML is treated as ordinary structured data and parsed using PowerShell's native XML support. The payload is then extracted from the resulting object structure and processed separately.

This distinction matters because defensive controls may monitor deserialisation-specific behaviours independently from ordinary XML parsing. XFA therefore investigates whether an equivalent payload reconstruction workflow can be achieved without relying on those deserialisation primitives.

7. Attack Scenario

A practical XFA attack chain can begin with an attacker gaining an execution opportunity on a Windows endpoint. The initial access mechanism is independent of XFA and may include a malicious document, script, compromised software, user-assisted execution, or another execution primitive.

Once PowerShell execution is available, the attacker can introduce the XML representation containing the encoded payload. The XML content itself can appear structurally similar to legitimate XML or CLIXML-style data.

PowerShell then parses the XML and accesses the relevant nodes. The payload is reconstructed in memory and decoded before being passed to ScriptBlock::Create().

From an attack-chain perspective, XFA therefore operates primarily as a payload representation and execution layer. It does not define how the attacker initially compromises the host, nor does it determine the final objective of the payload.

8. Defensive Evasion Characteristics

8.1. Separation Between Container and Payload

The XML representation separates the executable content from the initial PowerShell logic responsible for processing it. This can make the first representation of the payload substantially different from the final command that executes.

8.2. Legitimate Native Functionality

XFA relies on functionality that is normally available on Windows systems running PowerShell. XML parsing, object navigation, string handling, and dynamic PowerShell execution are not inherently malicious.

This creates an important detection challenge: individual events may have legitimate explanations even when the complete sequence forms part of a malicious execution chain.

8.3. In-Memory Reconstruction

The payload is reconstructed after the XML has been parsed and processed. The final PowerShell source therefore does not need to appear as a contiguous block in the original XML representation.

8.4. Reduced Dependence on Deserialisation

The technique does not require PowerShell's deserialisation primitives. This allows the research to investigate a different telemetry path from techniques that depend directly on ConvertFrom-CliXml or PSSerializer.Deserialize.

9. Detection Considerations

XFA should be detected through behavioural correlation rather than by relying exclusively on a single indicator.

Behaviour Potential Detection Value
PowerShell XML parsing Low by itself because XML processing is common administrative behaviour.
Access to XML payload nodes Potentially useful when combined with subsequent decoding and execution.
Encoded payload processing Useful as a contextual signal, particularly when followed by dynamic execution.
Dynamic ScriptBlock creation High-value behavioural signal when correlated with preceding payload reconstruction.
PowerShell execution after reconstruction Strong correlation point for endpoint detection systems.

9.1. PowerShell Telemetry

PowerShell ScriptBlock logging can provide visibility into dynamically generated script content depending on the PowerShell version and logging configuration.

Consequently, XFA should not be considered inherently invisible to PowerShell telemetry. The method instead represents a change in how the payload is represented before execution.

9.2. AMSI and Endpoint Telemetry

AMSI and endpoint security products may observe PowerShell execution at different stages of the attack chain. The effectiveness of XFA therefore depends on where a particular security product performs inspection.

A product that observes only the initial XML representation may have different visibility from a product that correlates the decoded ScriptBlock with the preceding XML processing operations.

10. Forensic Considerations

Investigators should not limit analysis to the initial XML content. The relevant evidence may exist across multiple telemetry sources.

  • PowerShell process creation events.
  • PowerShell ScriptBlock logging.
  • AMSI-related telemetry where available.
  • Parent-child process relationships.
  • Command-line parameters.
  • Files or resources containing the XML payload.
  • Network activity generated by the final payload.
  • Endpoint telemetry surrounding dynamic script execution.

Correlating these sources can allow defenders to reconstruct the complete execution chain even when the initial payload representation appears to contain only structured data.

11. MITRE ATT&CK Mapping

13. Limitations

XFA should not be interpreted as a universal EDR or AV bypass. Security products differ substantially in where and how they inspect PowerShell, XML, encoded data, AMSI content, and dynamically generated script.

The technique may also generate detectable behavioural signals. In particular, dynamic ScriptBlock creation and subsequent PowerShell execution may remain visible even when the original payload was embedded inside an XML representation.

The effectiveness of the method must therefore be established through controlled testing rather than inferred solely from the use of XML or encoded payload data.

14. Mitigation Recommendations

  • Enable PowerShell ScriptBlock logging where operationally appropriate.
  • Monitor suspicious PowerShell processes that perform XML parsing followed by dynamic script execution.
  • Correlate encoded-data processing with subsequent ScriptBlock creation.
  • Maintain AMSI and endpoint security telemetry.
  • Use Constrained Language Mode where appropriate.
  • Apply AppLocker or WDAC according to organizational requirements.
  • Monitor unusual parent-child PowerShell process relationships.
  • Investigate XML files or embedded XML data that are immediately followed by dynamic PowerShell execution.

15. Recommended Detection Logic

A practical detection strategy can focus on correlation rather than a single static signature. 

```

PowerShell process
│
├── XML parsing
│
├── XML node extraction
│
├── encoded-data reconstruction
│
├── decoding operation
│
└── ScriptBlock creation / invocation
│
▼
Elevated investigation priority
```

This approach reduces the probability of generating excessive alerts from ordinary XML parsing while increasing confidence when several behaviours occur within the same process execution chain.

16. Research Significance

The primary significance of this research is the investigation of a payload-delivery pattern that combines ordinary PowerShell XML processing with dynamic execution without requiring PowerShell deserialisation.

The research therefore focuses on the behavioural boundary between data processing and code execution. XML is initially treated as structured data; after several transformations, the same process converts that data into executable PowerShell.

This boundary is relevant to defenders because modern endpoint security increasingly relies on behavioural correlation rather than simple signature matching. A technique that deliberately distributes its execution logic across otherwise legitimate operations can therefore provide a useful case study for detection engineering.

17. Conclusion

XPath Fragment Assembly (XFA) describes a PowerShell execution pattern in which XML is used as an intermediate representation for executable payload data. The method relies on native XML parsing, XML object navigation, payload reconstruction, decoding, and dynamic ScriptBlock execution.

The principal security characteristic is the separation between the initial payload representation and the final executable PowerShell content. Rather than presenting the complete command as a contiguous script, the execution chain reconstructs the required content during runtime.

From a defensive standpoint, the technique demonstrates why individual operations such as XML parsing or encoded-data processing should not necessarily be treated as malicious in isolation. Correlation between XML processing, payload reconstruction, decoding, and dynamic execution provides a more meaningful detection strategy.

XFA should therefore be regarded as a research technique and detection case study. Further validation against multiple endpoint security products, PowerShell versions, logging configurations, and AMSI implementations would be required to determine its practical defense-evasion effectiveness.

Research conclusion: The important security property investigated by XFA is not the use of XML or encoded data individually, but the chaining of legitimate PowerShell capabilities into a runtime payload reconstruction and execution workflow.
