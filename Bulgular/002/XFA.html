XPath Fragment Assembly (XFA) – A PowerShell/XML Payload Assembly and Execution Method
Published: 9 August 2026 Author: BoxStrike Research Version: 1.4 Classification: Public

1. Introduction

This report documents a PowerShell execution pattern in which Base64-encoded payload data is stored as multiple XML text fragments, extracted from the parsed XML object, concatenated in memory, decoded, and subsequently passed to a PowerShell ScriptBlock.

The method is referred to in this research as XPath Fragment Assembly (XFA). The term describes the fragmentation and XML-based extraction stage of the execution chain. It does not imply that XPath itself performs code execution.

The core sequence is: XML parsing → extraction of <S> elements → fragment concatenation → Base64 decoding → ScriptBlock creation → execution.

Scope: XFA is presented as a research term for this particular execution pattern. It should not be interpreted as a formally established MITRE ATT&CK technique or as proof that every implementation of the pattern bypasses security controls.

2. Methodology

The technique consists of several independent operations. The security significance, if any, comes from their combination rather than from XML parsing or Base64 decoding individually.

  1. Payload preparation: A PowerShell test command is encoded as Base64.
  2. Fragmentation: The Base64 representation is divided into multiple fragments. The fragments must reconstruct the exact original Base64 string.
  3. XML embedding: Each fragment is stored inside an <S> element.
  4. XML parsing: PowerShell converts the XML string into an XML object using [xml].
  5. Fragment extraction: The Obj.S nodes are retrieved from the parsed XML object. This is XML node/property access; the term XPath Fragment Assembly refers to the overall research method rather than claiming that XPath itself executes the payload.
  6. Assembly: The extracted fragments are concatenated with -join ''.
  7. Decoding: The reconstructed Base64 string is decoded with [Convert]::FromBase64String().
  8. Execution: The resulting PowerShell source is converted to a ScriptBlock and invoked.

2.1. Base64 Length Verification

Base64 data must reconstruct to a syntactically valid Base64 representation. In particular, a Base64 string whose length has a remainder of 1 when divided by 4 is invalid and cannot be passed directly to FromBase64String().

An earlier version of this research contained 13 fragments whose combined length was 733 characters. Since 733 mod 4 = 1, that data was invalid for the decoding operation used by the PoC.

Correction in Version 1.4: The previous report incorrectly stated that the 13 fragments totalled 708 characters. That statement was incorrect. The original fragments totalled 733 characters. The PoC has therefore been regenerated rather than merely changing the documented length.

3. Proof of Concept

The following PoC uses a benign test command. Its purpose is to verify the XML fragment extraction, assembly, Base64 decoding, and ScriptBlock execution chain without establishing a network connection or executing an external command.

System.StringcHJvb2

System.StringY29uY2

```

3.2. Verification and Execution

```

# Parse XML

$xml = [xml]$xmlPayload

# Extract all S elements

$fragments = $xml.Objs.Obj.S

# Reconstruct Base64

$combinedBase64 = $fragments -join ''

# Verify reconstructed Base64 length

$combinedBase64.Length

# Expected: 76

# Decode

$fullCommand = [System.Text.Encoding]::UTF8.GetString(
[System.Convert]::FromBase64String($combinedBase64)
)

# Execute the benign test payload

& ([scriptblock]::Create($fullCommand))
```
Verification result: The regenerated PoC contains 13 fragments with a combined Base64 length of 76 characters. Therefore 76 mod 4 = 0, and the reconstructed Base64 representation satisfies the length requirement of the decoding operation.

After assembly and decoding, the test payload resolves to:

```

The expected output is a single line confirming that the complete XML extraction → assembly → decoding → ScriptBlock execution chain operated successfully.

4. Technical Interpretation

The individual operations used by the PoC are legitimate PowerShell and .NET functionality. XML parsing, string concatenation, Base64 decoding, and ScriptBlock creation are not inherently malicious operations.

The security-relevant characteristic investigated by this research is whether security products treat the complete sequence differently from equivalent payload delivery mechanisms in which the payload is presented as a contiguous string.

Consequently, the existence of the XFA execution pattern alone does not establish an EDR bypass. Such a claim requires controlled testing against specific security products and configurations.

4.1. Potential Detection Considerations

  • XML parsing immediately followed by Base64 decoding may form a useful behavioural signal.
  • Fragment concatenation followed by dynamic ScriptBlock creation can provide a stronger detection sequence than any individual operation.
  • ScriptBlock logging, AMSI, and other PowerShell telemetry may still expose the decoded or executed content depending on the environment.
  • Fragmentation does not inherently make the payload undetectable. It primarily changes how the payload is represented before execution.

6. MITRE ATT&CK Mapping

XFA is not a formally named MITRE ATT&CK technique. The individual behaviours used by the method may overlap with existing ATT&CK techniques, depending on the final payload and execution context.

Tactic ID Technique Relationship to XFA
Defense Evasion TA0005 Obfuscated Files or Information Base64 representation and payload fragmentation may constitute obfuscation.
Defense Evasion T1027.010 Command Obfuscation Applicable where the final command is intentionally transformed or fragmented.
Execution T1059.001 PowerShell The execution chain uses PowerShell.
Defense Evasion T1140 Deobfuscate/Decode Files or Information Base64 decoding reconstructs the PowerShell source.

7. Mitigation and Detection Recommendations

Defenders should focus on the complete behavioural sequence rather than treating XML parsing or Base64 decoding as malicious in isolation.

  • Monitor PowerShell processes that parse XML and subsequently perform Base64 decoding.
  • Correlate fragment extraction and string concatenation with dynamic ScriptBlock creation.
  • Enable PowerShell ScriptBlock Logging where appropriate.
  • Maintain AMSI and endpoint security telemetry in supported PowerShell environments.
  • Use application control mechanisms such as WDAC or AppLocker where appropriate to the environment.
  • Test detections against both contiguous and fragmented representations of the same benign test payload.

8. Research Limitations

The existence of a working assembly mechanism does not by itself establish a reliable defense-evasion capability. Detection effectiveness depends on the telemetry available to the security product and on the exact payload, PowerShell version, logging configuration, AMSI integration, and endpoint policy.

In particular, this report does not claim that XML parsing or Base64 fragmentation universally bypasses EDR/AV products. Such a conclusion would require reproducible testing across multiple products and configurations.

9. Conclusion

XPath Fragment Assembly (XFA) describes a PowerShell execution pattern in which payload fragments are embedded in XML, extracted from the parsed document, reassembled in memory, decoded, and passed to a ScriptBlock.

The original PoC contained a reproducibility error: its 13 fragments totalled 733 characters, while the report incorrectly stated that they totalled 708 characters. Because 733 has a remainder of 1 when divided by 4, the original value could not be decoded by the documented FromBase64String() operation.

Version 1.4 resolves this inconsistency by regenerating the PoC with a verified Base64 payload rather than modifying the reported length alone. The corrected demonstration contains 13 fragments totalling 76 characters and successfully exercises the intended XML extraction, fragment assembly, decoding, and ScriptBlock execution chain.

Future research should evaluate whether this representation produces a measurable detection difference compared with equivalent contiguous payloads. Such controlled experiments are necessary before describing XFA as a demonstrably effective defense-evasion mechanism.
