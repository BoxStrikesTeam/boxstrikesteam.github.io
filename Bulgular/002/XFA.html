BoxStrike · Finding 002

XPath Fragment Assembly (XFA) – A Novel Defense Evasion Technique in PowerShell
Published: 7 August 2026 Author: BoxStrike Research Team Version: 1.2 Classification: Public

1. Introduction

PowerShell has become an indispensable tool for system administration in the Windows ecosystem. However, its power also makes it one of the most frequently abused vectors by attackers. Commands such as Invoke-Expression, IEX, and ConvertFrom-CliXml are heavily monitored by Endpoint Detection and Response (EDR) and Antivirus (AV) solutions.

The BoxStrike research team has developed a new defense evasion technique that leverages PowerShell's CLIXML serialization format and XPath querying capabilities to bypass existing detection mechanisms. We call this technique XPath Fragment Assembly (XFA).

XFA embeds a malicious payload inside an XML file as Base64-encrypted fragments. On the target system, the XML is read and parsed without any deserialization calls—only XPath queries are used. The fragments are then assembled, decoded, and executed. This approach successfully evades both signature‑based and behavioral detection.

Key observation: This technique does not require administrative privileges. The XML file can be read and processed with standard user rights, which significantly increases the threat surface.

2. Technical Background

2.1. CLIXML and PSSerializer – The Foundation

PowerShell's proprietary serialization format, CLIXML, is used to store complex .NET objects along with their properties and type information in XML. This format is the backbone of data exchange in PowerShell Remoting, Hyper-V, and many other technologies.

The [System.Management.Automation.PSSerializer]::Deserialize() method takes a CLIXML string and reconstructs a PowerShell object in memory. However, the resulting object is not a live copy of the original—it is merely a snapshot. During serialization, the object's runtime behavior (methods) is discarded; only the data itself is preserved.

In the XFA method, we use this deserialization only to retrieve System.String objects from the XML. These strings are Base64-encoded fragments of the final payload. After deserialization, we have an array of strings. We then concatenate all fragments first and only then decode the combined Base64 string. This is a crucial step because Base64 decoding requires the total length to be a multiple of 4.

2.2. XPath and XML Parsing in PowerShell

PowerShell's [xml] type accelerator converts an XML string into an XmlDocument object, which supports XPath queries. XPath is a standard language for navigating XML documents and selecting specific nodes.

In XFA, the expression $xml.Objs.Obj.S retrieves the content of all <S> tags—i.e., the Base64-encoded fragments—in one go. This operation does not involve deserialization and is a perfectly legitimate XML parsing activity. EDR/AV systems typically treat such XML reading as routine configuration file access.

3. XFA Methodology

The XFA technique consists of the following steps:

  1. Payload preparation: The attacker converts the desired command (e.g., a reverse shell) to a Base64 string.
  2. Fragmentation: The Base64 string is split into an arbitrary number of fragments (e.g., 5–10). Each fragment is placed inside a <S> tag in CLIXML format.
  3. XML assembly: All fragments are combined into a valid CLIXML document.
  4. Delivery: The XML file is delivered to the target system (via email, web download, USB, etc.).
  5. Parsing on target: The XML is read using Get-Content and cast to [xml]. No deserialization is performed; only XML DOM parsing (XPath) is used.
  6. Fragment assembly: The content of all <S> tags is retrieved via XPath. All fragments are concatenated first to form a single, complete Base64 string.
  7. Decoding and execution: The combined Base64 string is decoded to the original command, which is then converted into a ScriptBlock using [scriptblock]::Create() and executed with the & operator.
Important correction: Earlier versions of this PoC incorrectly attempted to decode each fragment individually. This fails because Base64 strings must be decoded as a whole (length multiple of 4). The corrected method concatenates all fragments before decoding.

4. Proof of Concept (PoC)

Two variants of the XFA method are presented below. In the first, the XML file resides on disk; in the second, the XML is embedded directly in the script (as a here‑string). Both variants are designed to open a reverse shell connection.

6. Why It Evades Detection – "Lost in the Noise"

To understand why XFA evades detection, we must examine how EDR/AV systems operate. These systems typically look for:

  • Known malicious commands: Invoke-Expression, IEX, calc.exe, etc.
  • Anomalous PowerShell behaviour: Long or repetitive command lines, suspicious code execution patterns.
  • Deserialisation operations: Calls to ConvertFrom-CliXml or PSSerializer.Deserialize followed by code execution.

XFA bypasses these mechanisms as follows:

  • A. The payload is fragmented and encrypted. The <S> tags contain only Base64-encoded fragments of the reverse shell code. Individually, they contain no IEX or calc.exe keywords. Static analysis sees only harmless text.
  • B. No deserialisation is used (in PoC 1). Instead of ConvertFrom-CliXml or PSSerializer.Deserialize, we use [xml] and XPath. This is a perfectly legitimate XML parsing operation that does not raise any alarms.
  • C. The malicious code is created in memory at runtime. The final command is assembled and converted to a ScriptBlock only in memory. It never touches the disk in executable form.
  • D. The final execution step looks normal. & ([scriptblock]::Create(...)) is less well‑known than Invoke-Expression and is not yet widely monitored by EDRs.

Thus, XFA operates under the radar by blending in with legitimate system activity—a classic "lost in the noise" strategy.

9. Potential Use Cases

XFA can be employed in the following scenarios:

  • Red Team operations: Authorised penetration tests that require EDR/AV evasion.
  • Advanced Persistent Threat (APT) campaigns: Actors seeking long‑term stealth.
  • Phishing campaigns: Malicious XML files sent as email attachments, tricking the target into executing them.
  • Side‑channel attacks: XML fragments can be distributed via DNS, HTTP, or other protocols.

Moreover, this technique is not limited to reverse shells. Any PowerShell command (e.g., file download, registry modification, data exfiltration) can be concealed using the same method.

10. Detection and Mitigation Recommendations

To detect and prevent this technique, the following measures are recommended:

  • XML content analysis: Monitor XML files for long Base64 strings and unusual <S> tags. These may indicate fragmented payloads.
  • PowerShell ScriptBlock logging: Analyse usage of [scriptblock]::Create() and the & operator for suspicious patterns.
  • Constrained Language Mode: Restrict PowerShell to prevent deserialized objects from being executed.
  • AMSI integration: Keep AMSI (Antimalware Scan Interface) updated and active in all PowerShell sessions.
  • AppLocker / WDAC: Limit PowerShell script execution to signed or approved scripts only.

11. Conclusion

The XPath Fragment Assembly (XFA) method leverages legitimate XML operations and Base64 encryption to make malicious payloads nearly invisible to detection systems. In the on‑disk scenario, the detection rate was 0 out of 62 antivirus engines on VirusTotal. This demonstrates that current security products are not yet equipped to handle such "lost in the noise" techniques.

This research highlights that operations considered "legitimate" (XML reading, string concatenation, Base64 decoding) can be chained into an effective attack chain. Attackers can easily bypass security products using such Living Off the Land techniques.

BoxStrike is publishing this report publicly to raise awareness and encourage EDR vendors to incorporate detection for these behavioural patterns.
