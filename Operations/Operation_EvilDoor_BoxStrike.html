1.Executive summary

BoxStrike researchers have identified and documented a distribution operation, which we track as Operation EvilDoor, that delivers the previously-documented Android ad-fraud family Konfety to victims searching for Roblox game cheats, executors, and exploits. The operation has been active since 2024 through YouTube video descriptions and, in the months preceding this report, expanded to a second, more scalable channel: a network of disposable GitHub accounts publishing search-optimized, AI-authored repository pages themed around the Roblox game DOORS and similar titles.

A sample obtained directly from this GitHub network was decompiled and analyzed both statically and dynamically by BoxStrike. The sample matches the Konfety family with high confidence: it smuggles a fully encrypted, second-stage DEX payload inside a booby-trapped ZIP asset and loads it directly into the app's classloader in memory at runtime, a technique that defeats static scanning entirely. Two independent public sandboxes corroborated this behavior executing live, down to the exact obfuscated class names appearing as dropped files on disk.

This report's contribution is not the discovery of a new malware family — Konfety is already tracked by the wider security community — but the documentation of a previously unreported distribution vector for it, together with a full architectural breakdown of why the malware is built the way it is, not only what it does.

2.Background and timeline

The fake Roblox cheat marketplace behind Operation EvilDoor has run since 2024, primarily through YouTube video descriptions promising working executors and exploits, with download links placed below gameplay footage. This channel remains active in parallel with the newer one described in this report.

Roughly three months before this report's publication, the same operators (or a closely related group reusing the same playbook) opened a second channel on GitHub: dozens of new accounts began publishing long-form, professionally formatted repository pages for tools with names like "Doors Script Hub," "Rooms and Doors Toolkit," and various generically-named "executors," each ultimately funneling the visitor to a malicious download.

Analyst commentary — why the pivot to GitHub A YouTube-only distribution model has a structural weakness for the operators: video takedowns are fast, comments and descriptions are moderated, and the platform actively demotes content associated with malware reports. GitHub, by contrast, is widely treated as an inherently trustworthy domain by both end users and network security tooling — many corporate web filters and parental-control products do not flag github.com or *.github.io at all, since the domain is core developer infrastructure. Moving distribution to GitHub buys the operators a second channel that benefits from that borrowed trust, free HTTPS hosting via GitHub Pages, and a search-engine-friendly surface (repository READMEs are indexed and rank well for the exact search terms — "roblox executor," "doors script" — that the victim population is already typing into Google or an AI assistant).

3.Operation EvilDoor modus operandi

Across the accounts reviewed, Operation EvilDoor follows a consistent four-stage chain from lure to payload execution.

Figure 1. Simplified scheme of the GitHub-based delivery chain used in Operation EvilDoor.

The victim discovers a repository while searching for a Roblox executor or script, either directly on GitHub or via a search engine that has indexed the README's keyword-dense content. The repository itself contains no functional tool — its only job is to look credible for exactly as long as it takes the visitor to click through to a download page hosted on the same account's GitHub Pages subdomain. That page is engineered to look like an official GitHub-branded download portal and drives the visitor toward executing the downloaded file with minimal friction.

Analyst commentary — target selection Roblox's player base skews young, and the specific demand being served here — free, working "executors" that inject arbitrary code into a game client to cheat — is itself already a security-adverse request: a working executor is, by definition, a tool designed to bypass anti-cheat protections, so the target audience is pre-selected for a willingness to disable protective controls (antivirus exclusions, "install from unknown sources," ignoring browser warnings) in pursuit of the tool. This is not incidental; it is very likely the reason this demographic and this specific search-intent category were chosen as the lure, independent of which payload family happens to be served through it at any given time.

Independent, read-only inspection of a representative account (doorsrbx/doors) confirmed the following, which the naming pattern above suggests is shared across the set:

  • No functional source code in the repository — in this case two files only (LICENSE.md, index.html), three commits, zero stars, forks, or watchers.
  • A multi-thousand-word README written as a marketing landing page: feature lists, fabricated user testimonials, an executor-compatibility table, hardware "system requirements," and dense repetition of search-intent keywords ("doors script github," "doors script pastebin 2026," "doors scriptblox") consistent with LLM-generated SEO copy rather than genuine documentation.

Analyst commentary — why an AI-written README, specifically The repetitive, keyword-saturated structure of the README is not a stylistic accident: it is optimized for two audiences simultaneously — the human visitor skimming for credibility signals (testimonials, a feature table, "system requirements"), and the search/ranking algorithms (GitHub's own search, Google, and increasingly AI chat assistants that summarize search results) that reward keyword density and content length. Generating this at scale across 20+ accounts by hand would be labor-intensive; an LLM can produce a plausible, on-topic wall of text for a new repository in seconds, which is almost certainly why the account-creation and content-publishing pattern observed here looks semi-automated rather than bespoke.

4.2 The download portal

The linked GitHub Pages site presents as "Download Ready — Secure Archive." It imitates GitHub's own site chrome, displays a green "Verified" badge alongside unearned "100% Safe / Protected / Encrypted" labels, and runs an auto-starting countdown timer straight into a download action.

Analyst commentary — why the countdown and fake badges work This page design borrows directly from two well-studied influence principles: authority (imitating GitHub's own branding transfers the platform's credibility onto the page) and urgency (the countdown removes the natural pause in which a visitor might otherwise open a new tab to check the tool's legitimacy). Neither the "Verified" badge nor the "100% Safe" label is backed by any actual verification process — they are static images placed for their psychological effect, not functional trust indicators. This is a low-cost, high-yield technique: it requires no server-side logic, only a convincing static page, and it is trivially reproducible across every account in the network.

5.Konfety malware architecture

5.1 The decoy layer

The APK bundles a full set of legitimate, functioning ad-mediation SDKs: AppLovin, Unity Ads, Chartboost, Vungle, Pangle, BigoAds, Fyber, AdMob, Meta Audience Network, and Firebase. This is the layer a cursory static scan sees, and it is convincing enough on its own that the sample presents as an unremarkable ad-monetized app.

Analyst commentary — why bundle real ad SDKs at all Bundling genuine, functioning ad SDKs serves two purposes simultaneously. First, it gives the app a legitimate monetization path independent of the hidden payload, meaning the app is not only malicious — it is a real (if low-quality) ad-supported app that happens to also carry a hidden loader, which raises the bar for both automated classifiers and human reviewers who are looking for an app that does nothing but harm. Second, and more directly tied to Konfety's known "evil twin" model (see §7), the visible ad SDK traffic gives the app a plausible reason to make constant network requests — which helps mask the C2 registration and remote-config traffic described in §9 inside what looks like routine ad-network chatter.

5.2 Entry point and control-flow obfuscation

Execution begins in the app's Application subclass:

public final class BLAcKr extends Application {
    private final Fqb wbCfMcQ = new Fqb();

    protected void attachBaseContext(Context context) {
        ILHwmX = context;
        this.wbCfMcQ.run();
        super.attachBaseContext(...);
    }
}

run() routes through an eight-method call chain interleaved with calls that produce no useful output — System.nanoTime(), Locale.getDefault(), Environment.getRootDirectory():

run → ILHwmX → tNF → tBKiQ → pOEXilH → cKVP → NfxL → ZyKCx → [payload logic]
Analyst commentary — why pad the call graph instead of just hiding the logic This technique targets the economics of manual reverse engineering rather than any specific detection signature. A decompiled call graph with eight hops and interleaved no-op API calls costs an analyst real time to trace by hand, and automated tools that flag "suspicious" API usage (dynamic class loading, reflection) are less likely to surface a short, clearly-suspicious function if it is buried eight calls deep behind functions that look benign at each individual step. The technique does not defeat analysis — as this report demonstrates — but it raises the cost of analysis, which for a high-volume, disposable-build operation is often sufficient: the goal is not to be unbreakable, it is to outlast the average analyst's patience and the average scanner's static call-depth limit.

5.3 String encryption

Every reflection target — class names, method names, the payload's asset filename — is stored XOR-encrypted, keyed by a custom reimplementation of java.util.Random's LCG algorithm, seeded by each string's own length. Reproducing the algorithm recovers the plaintext:

"g}~e\u007fk7cgad`j$JfzQwivPjkp"    -> "dalvik.system.DexPathList"
"d\u007fmv_yZ\u007fdwmeJ~oXcbydezf" -> "makeInMemoryDexElements"
"ws`nwn<|fc}\u007fn DmeuIyvY}mkoGm\u007fot}" -> "dalvik.system.BaseDexClassLoader"
"rh`Sfihja"                        -> "getAssets"
"zwt|"                             -> "open"
"Ejzqa"                            -> "Mbqct"
"xciaft\u007f"                     -> "classes"
Analyst commentary — why reimplement Random instead of using a standard cipher Reimplementing java.util.Random's algorithm by hand, rather than calling the real class, is a deliberate choice aimed at static-signature evasion: many mobile security products flag the literal bytecode signature of constructing a java.util.Random instance and calling nextInt/nextBytes near a Class.forName call, since that combination is a known indicator of runtime string decryption. By hand-rolling an identical algorithm under an obfuscated class name, the malware achieves the same cryptographic result while avoiding the specific API call pattern that a signature-based detector is likely to be watching for. It is a functionally pointless but detection-relevant distinction — the seed constant it depends on is, as it happens, exactly the kind of durable artifact that survives this evasion (see §11).

5.4 The hidden payload

assets/Mbqct is a genuinely valid ZIP file containing harmless auto-generated resource-ID stub classes, including a com/nextg/... package path — likely a remnant of the app's original, pre-repackaging identity. The ZIP's official End-Of-Central-Directory record places its true end at byte 146,739 of a 2,395,655-byte file, leaving 2,248,916 bytes appended after the archive's stated end, invisible to standard archive tools.

Analyst commentary — why hide data past the ZIP's declared end, specifically An APK is itself a ZIP file, and the overwhelming majority of both automated scanners and human analysts inspect an APK's contents by asking the operating system's or a library's ZIP parser to enumerate its entries — which, by design, only reads what the central directory declares. Data appended after the declared end is invisible to that entire class of tooling without ever being "encrypted" in a way that would itself look suspicious to a file-type classifier; the outer file still reports as a normal, well-formed ZIP/APK. This is a lower-effort, higher-yield evasion than encrypting the whole APK, because it requires no custom unpacking stub in the visible code path at all — only a component that knows to keep reading past where every other tool stops.

At runtime, the app reads the full file, XOR-decrypts it against a keystream from a fixed-seed java.util.Random(4339707483826144610L), skips a pseudo-randomized offset, and parses the remainder as a second ZIP stream:

Random random = new Random(4339707483826144610L);
for (int i = 0; i < iAvailable; i++) {
    bArr[i] = (byte) (bArr[i] ^ iNextInt);
}
int offset = new Random(4339707483826144610L).nextInt(307201) + 204800;
ZipInputStream zip = new ZipInputStream(
    new ByteArrayInputStream(bArr, offset, iAvailable - offset));

Reproducing this algorithm confirms a valid ZIP local header at decrypted offset 207,084, containing a single entry: classes.dex — a complete, independent Android program never visible anywhere in the outer APK.

Analyst commentary — why a fixed seed instead of a per-build random key Using a hardcoded seed rather than generating a fresh key per build is, from the operator's perspective, almost certainly a convenience decision rather than a security one: it means the same build tooling can encrypt a payload once and reuse the identical decryption stub across every app built from that toolkit, without needing to manage or distribute per-sample keys. The tradeoff is that this constant becomes a durable artifact investigators can search for across future samples regardless of how the surrounding obfuscation is reshuffled — precisely the property this report's YARA signature (§11) is built around.

5.5 In-memory injection

classes.dex is spliced directly into the running app's ClassLoader via reflection, without ever touching disk as a standalone file:

Method m = Class.forName("dalvik.system.BaseDexClassLoader")
             .getDeclaredMethod("makeInMemoryDexElements", ...);
m.setAccessible(true);
Object newElements = m.invoke(null, dexBytes, null);
// merged into pathList.dexElements via reflection
Figure 2. Internal payload-loading chain inside the Konfety sample analyzed for this report.
Analyst commentary — why in-memory injection instead of writing a second APK or service Loading the payload purely in memory, rather than dropping it as an installed component, sidesteps two separate detection surfaces at once: Android's package manager never sees a second app to flag, and no new file with a suspicious hash persists on disk between reboots for an on-demand or scheduled AV scan to find. The cost to the operator is that the payload must be re-decrypted and re-injected every time the process restarts — which is an acceptable tradeoff for an ad-fraud operation that only needs the payload live while the app is in the foreground or running as a background service generating traffic, not a persistent, always-on implant.

Analyst commentary — why clipboard monitoring in an ad-fraud family Clipboard monitoring costs the operator almost nothing to add — addPrimaryClipChangedListener requires no special manifest permission and adds negligible code — while opening a second, unrelated monetization path: any cryptocurrency wallet address, password, or one-time code a victim copies during normal phone use is harvested for free alongside the ad-fraud functionality. This is best read as opportunistic scope creep rather than a core design goal of the family, but it is precisely why sandbox vendors tag this sample with both infostealer and adware labels rather than one or the other.
Analyst commentary — why query MCC/MNC and geolocation before generating ad traffic Ad-fraud revenue is geography-dependent: cost-per-impression and cost-per-click rates paid by ad networks vary substantially by country, and some ad-fraud detection platforms apply stricter scrutiny to traffic from specific regions. Querying the mobile country code before generating fraudulent impressions lets the operators selectively throttle or redirect behavior toward the highest-yield or lowest-scrutiny geographies, and the remote-config fetch observed in this sample (§9) is the mechanism by which that behavior can be updated centrally without shipping a new app build.

7.Family attribution

Both sandboxes independently tag the sample Konfety. The technique matches published research on the family closely enough to treat attribution as high-confidence.

"The Konfety malware family first emerged as part of a massive mobile advertising fraud campaign that was initially disrupted by security researchers in 2024. The original operation involved more than 250 decoy applications on Google Play Store, each paired with malicious 'evil twin' counterparts distributed through third-party channels. At its peak, the campaign generated an astounding 10 billion fraudulent ad requests per day." — cited from public threat research
"Konfety includes an encrypted secondary DEX file within its APK, which is decrypted at runtime. This allows the installation of additional malicious modules dynamically." — cited from public threat research
Analyst commentary — why the "evil twin" model specifically Publishing a genuinely harmless "twin" app on the Google Play Store under the same package name and branding as the malicious version accomplishes something the GitHub lure alone cannot: it gives the operation a legitimate, reviewable, Play-Protect-scanned artifact to point to if questioned, while the actual malicious distribution happens entirely outside Google's review pipeline through GitHub and YouTube. A victim (or a cursory automated check) who searches for the app name and finds a real, functioning Play Store listing has little reason to suspect the file they downloaded from a GitHub Pages link is anything other than the same app obtained through a different channel. This is the same trust-transfer logic used by the download-portal branding in §4.2, applied one layer up, at the level of app identity rather than page design.

What this report adds: prior public research documents Konfety's distribution via third-party app stores and package-name-spoofed "evil twin" apps. This is, to BoxStrike's knowledge, the first documentation of the same payload family being funneled through a GitHub-hosted, Roblox-cheat-themed lure network — an additional distribution vector for an already-tracked family, not a new family.

9.Infrastructure and command and control

No passive DNS, WHOIS registration-date, or hosting-provider pivot was performed for this report; these domains are provided as first-order network indicators only.

Analyst commentary — the anti-fraud check-in The sample's observed communication with cdntechone.com, an anti-ad-fraud detection platform, is most plausibly explained as the operators monitoring their own traffic's detection status rather than any legitimate integration. This is a recurring pattern in ad-fraud tooling generally: operators build feedback loops against the very detection systems designed to stop them, using the results to decide when to rotate infrastructure or throttle behavior in a given ad network before their traffic is blocklisted.

10.Actor attribution assessment

Confidence: low.low confidence No technical evidence in this analysis ties the operation to a specific named threat actor or nation-state.

  • The operation is consistent with a financially motivated ad-fraud and credential-collection operation rather than an espionage-driven one — the payload's design (ad SDK bundling, remote-config-driven fraud traffic, opportunistic clipboard monitoring) points to monetization, not targeted intelligence collection.
  • Public research on the Konfety family has previously noted Russian-language artifacts in earlier campaign infrastructure. reported, not independently verified
  • The GitHub distribution wave's account-creation pattern (batch-created, single-purpose, disposable) suggests a semi-automated operational workflow rather than manual, bespoke targeting.

This assessment should be treated as a starting hypothesis for further collection, not a conclusion. BoxStrike does not attribute this activity to any nation state; our use of the term "operation" refers to a coordinated distribution and monetization effort, not a state-directed campaign.

11.Detection guidance

11.1 YARA (static)

rule Konfety_EvilDoor_HiddenPayload
{
    meta:
        description = "Detects Konfety-family Android droppers using the EvilDoor technique: XOR-encrypted secondary DEX appended after a decoy ZIP asset's EOCD record"
        family = "Konfety"
        operation = "EvilDoor"
        author = "BoxStrike - Eneshan Erdogan Karaca"
        tlp = "CLEAR"

    strings:
        // Fixed PRNG seed (4339707483826144610) used to key the XOR keystream
        $seed_le = { 62 C5 8F BA F6 BC 39 3C }
        $seed_be = { 3C 39 BC F6 BA 8F C5 62 }

        // Obfuscated class/package identifiers observed in this sample family
        $cls1 = "viewcb/lej" ascii
        $cls2 = "ILHwmX" ascii
        $cls3 = "wbCfMcQ" ascii
        $cls4 = "BLAcKr" ascii

        // Reflection targets used for in-memory dex injection
        $api1 = "makeInMemoryDexElements" ascii
        $api2 = "dalvik/system/DexPathList" ascii

        $eocd = { 50 4B 05 06 }

    condition:
        uint32(0) == 0x04034b50
        and (any of ($seed_le, $seed_be)
             or (2 of ($cls1, $cls2, $cls3, $cls4))
             or any of ($api1, $api2))
        and for any i in (1..#eocd):
            (filesize - @eocd[i] > 200)
}

Note: the class-name strings are sample-specific to this obfuscator run and will rotate across builds — the seed-constant and trailing-data conditions are the more durable detection surface, precisely because of the build-tooling tradeoff discussed in §5.4.

12.Recommendations

  • Block the listed C2/redirect domains at network egress where feasible.
  • Treat any "download our tool from GitHub, then run it" flow from an unofficial source as high-risk by default, particularly when the repository contains no functional source code.
  • Never grant AV/Defender exclusions at the request of a downloaded tool's install instructions.
  • Mobile threat defense vendors should prioritize detection on the dex-injection-then-beacon behavior chain (§11.2) over static hash matching, since the obfuscator output — and likely the payload family — will continue to rotate.
  • Parents and guardians of Roblox players: executors and cheat scripts are, by construction, third-party code injection tools; there is no way to run one "safely" from an unverified source regardless of how polished the accompanying README or download page appears.

13.Conclusion

Operation EvilDoor is best understood not as a new threat, but as an existing, well-documented ad-fraud family — Konfety — being fed through a new, low-cost distribution surface that trades on the borrowed trust of GitHub and the specific vulnerability profile of a young, cheat-seeking audience already primed to disable their own protections. The technical sophistication observed in the payload (in-memory DEX injection, custom string encryption, steganographic asset abuse) is real and non-trivial, but it exists in service of a financially motivated ad-fraud and opportunistic data-collection operation, not a targeted intrusion.

BoxStrike will continue monitoring this distribution network and the Konfety family's evolution, and will publish updates as new samples, infrastructure, or distribution vectors are identified.
